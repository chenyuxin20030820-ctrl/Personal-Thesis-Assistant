# 个人论文助手：AI 产品经理实习简历表述

以下表述区分**已落地功能**和**已设计、待开发方案**。面试演示时可直接说明每项状态，不使用未经测量的用户数、准确率或效率提升。

## 简历版（建议 4 条）

**个人论文助手｜AI 产品经理项目实践**  
负责需求拆解、原型与流程设计，并推动 Python/FastAPI、LangChain、MySQL 的本地产品实现。

- 围绕“文献检索—筛选入库—精读分析—成果归档”设计多页面工作流，打通检索结果、精读任务、个人文献库及 Zotero；支持任务记录、结果恢复与失败重试。
- 设计中英文文献检索策略：OpenAlex 优先、SerpApi 补充，按年份和语言筛选并持久化结果快照；对仅有摘要的结果明确标注证据不足，避免输出未经原文支持的研究方法与实证结论。
- 落地翻译与阅读报告双 Agent 流程：英文论文逐段翻译并保存进度，阅读报告 Agent 递进阅读全文、按应用预算压缩事实记忆，依据用户上传模板生成中文报告。
- **完成后续方案设计（待开发）：**规划基于个人文献库的 RAG 对话链路，覆盖用户级文献切片、Embedding、向量召回与引用溯源；规划检索结果逐篇受控并发 AI 分析，包含证据分级、结构化输出、缓存和失败重试。

## 面试时如何说明边界

- **已完成：**AI 对话可使用当前会话的上传附件；文献检索、精读、模板报告、文献库和任务记录有可运行链路。
- **未完成：**对话尚未从整个人文献库做向量召回；检索结果尚未逐篇并发调用模型生成四项分析。它们是产品/技术方案，不是已上线功能。
- **可解释的设计取舍：**先保证文献来源、原文获取和证据边界，再扩展 RAG 与批量分析；避免把检索片段推断成论文全文结论。实现前还需解决多用户身份隔离、Embedding 模型与向量存储选型、调用成本和质量评估。

建议只有在完成实际开发、测试和效果评估后，才将第四条中的“规划”改为“实现”，并补入真实可核实的指标。
